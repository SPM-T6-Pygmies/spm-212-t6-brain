# User Account

The record of a person who interacts with the system — ConnectSphere internal staff or an external client-side / attendee user — carrying identity, contact and role information. Every other domain object attributes ownership, assignment or authorship to a User Account. Process detail lives in [[user-roles]] and [[access-control]]; this page is the structural reference.

## States

No account-level lifecycle (e.g. active / suspended / deactivated) is specified in either source. [#59](https://github.com/SinYang13/IS212-2026/discussions/59) asks what happens to an Event Organiser's events "if their account is deactivated" — the question presupposes deactivation as a concept, but the answer addresses only event ownership ("We can use the change of event organiser") and does not confirm that account deactivation itself is a modelled state. Whether a User Account carries a status field, and what would gate or trigger it, is left to the team (🔶 [#59](https://github.com/SinYang13/IS212-2026/discussions/59)).

## Binding rules

- A person may hold multiple roles at once ([#56](https://github.com/SinYang13/IS212-2026/discussions/56)); permission checks must therefore resolve per event, not per account — see [[access-control]].
- Venue Staff and Technical Support Staff access is governed by role and responsibility, and is explicitly **not** scoped by venue, equipment type, or location ([#66](https://github.com/SinYang13/IS212-2026/discussions/66)).
- Delegation of the Event Organiser role for a specific event is **not** supported; only a change of Event Organiser is supported, for handing off a single event to a colleague in the same organisation ([#61](https://github.com/SinYang13/IS212-2026/discussions/61)). [#59](https://github.com/SinYang13/IS212-2026/discussions/59)'s answer also points to this same change-of-organiser mechanism when asked about a "deactivated" account — but as the States section notes, the question presupposes account deactivation as a modelled concept that the answer never confirms, so treat that particular scenario as unconfirmed, not settled (🔶 [#59](https://github.com/SinYang13/IS212-2026/discussions/59)).
- An Event Organiser belonging to the same client organisation as an event's owner gets **view-only** access to that event and cannot edit or update it; an Event Organiser must not access events belonging to unrelated client organisations ([#81](https://github.com/SinYang13/IS212-2026/discussions/81)).
- An Event Coordinator may be assigned to two or more events concurrently; no workload cap is specified ([#92](https://github.com/SinYang13/IS212-2026/discussions/92)).
- The Event Operations Manager (now the Event Coordinator Lead) is a **separate system role**, not a permission on a senior Event Coordinator and not an out-of-system actor whose decisions are merely recorded; the detailed access-control implementation is 🔶 team decision, bounded by "only authorised users can perform these assignment functions" ([#101](https://github.com/SinYang13/IS212-2026/discussions/101)).
- No account onboarding or self-registration feature is required for Release 1. **Pre-loaded staff accounts** with the appropriate roles and access controls may be used for ConnectSphere employees, and **pre-loaded client accounts** for Event Organisers ([#49](https://github.com/SinYang13/IS212-2026/discussions/49)). Authentication itself remains required.
- Since [[week-7-customer-changes|Week 7 C5]], a newly submitted request enters an unassigned queue and the **Event Coordinator Lead** assigns and reassigns Event Coordinators; Event Coordinators manage **only** events assigned to them. The Lead is the Event Operations Manager retitled — the role "was already included as part of the requirement" ([#128](https://github.com/SinYang13/IS212-2026/discussions/128)) — and views all coordinators' assignments, so no coordinator-to-Lead link is needed. The queue needs no new data on this page: it is a request with status `Submitted` and no assigned coordinator. Whether the stored role name changes, or only the displayed title ("at least on the display end"), is 🔶 team decision ([#101](https://github.com/SinYang13/IS212-2026/discussions/101), [#128](https://github.com/SinYang13/IS212-2026/discussions/128)).
- A Lead's or Safety Officer's view of an event rests on a legitimate relationship to it and a need for their role, not on the role alone ([#125](https://github.com/SinYang13/IS212-2026/discussions/125)). See [[access-control]].
- Coordinator selection for a given event is entirely up to the Event Operations Manager, following an SOP maintained outside the system — no selection criteria need to be encoded ([#93](https://github.com/SinYang13/IS212-2026/discussions/93)).
- Reassignment of an event to a different coordinator is performed only by the Event Operations Manager; the system may assume any reassignment entered has already been approved ([#94](https://github.com/SinYang13/IS212-2026/discussions/94)).
- There is no acceptance step for a coordinator assignment or reassignment — it takes effect immediately and cannot be declined in the system; issues are handled outside the system ([#95](https://github.com/SinYang13/IS212-2026/discussions/95)).

## Open modelling questions

> [!question]- Team decision required — authentication method
> Secure authentication is required, but the method (email/password, SSO, MFA) is not specified: "Secure authentication is required, but the authentication method is not specified. Please propose an appropriate approach." ([#62](https://github.com/SinYang13/IS212-2026/discussions/62)).

> [!question]- Team decision required — account recovery and lockout
> Account recovery and locked-account handling are not specified in the current requirements ([#64](https://github.com/SinYang13/IS212-2026/discussions/64)).

> [!success] Resolved — [#49](https://github.com/SinYang13/IS212-2026/discussions/49)
> Account onboarding and self-registration are **not required for Release 1** — for either population. ConnectSphere employees: "No separate self-registration/onboarding feature is required for Release 1. The team may use **pre-loaded staff accounts** with the appropriate roles and access controls." Event Organisers: "account onboarding or self-registration is not required for Release 1. **Pre-loaded client accounts** may be used for testing." ([#49](https://github.com/SinYang13/IS212-2026/discussions/49)). The same answer states flatly that "Authentication is required" and that Attendee Registration "refers to event registration, not account creation". **What it does not settle is the Attendee path**: pre-loaded accounts are offered to staff and clients only, so an account-less registrant still holds a `registration_reference` and no credential — see [[registration]] and [[access-control]].

> [!question]- Team decision required — admin role and system configuration
> Whether an administrative role above the briefed stakeholders exists. The customer states no system-configuration feature is specified and user administration is not defined as a separate business role, inviting a proposal only if the solution requires it ([#52](https://github.com/SinYang13/IS212-2026/discussions/52)). Narrower since [#49](https://github.com/SinYang13/IS212-2026/discussions/49): pre-loaded accounts cover the initial population, so only ongoing administration is at stake. The Event Operations Manager (now the Event Coordinator Lead) does not fill this slot — [#101](https://github.com/SinYang13/IS212-2026/discussions/101) gives it assignment authority, not user administration.

> [!question]- Team decision required — field-level access-control design
> The exact access-control design and field-level permissions are explicitly delegated to the team; the customer gives only the categories of protected information (internal planning, venue/equipment arrangements, attendee information, client-related information, other non-public details), not a matrix ([#91](https://github.com/SinYang13/IS212-2026/discussions/91)).
